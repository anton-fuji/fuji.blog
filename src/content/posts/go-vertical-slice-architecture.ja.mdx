## はじめに

垂直スライスアーキテクチャ（Vertical Slice Architecture、以下VSA）という言葉自体は以前から知っていました。
ただ、「機能ごとに分ける」という説明だけでは、なぜそれが嬉しいのか、いつレイヤード構成より良い選択になるのかを、自分の言葉で説明できませんでした。

GoでHTTP APIを書くときは、`handler`、`service`、`repository` のように技術的な責務でパッケージを分ける構成をよく見かけます。この構成は分かりやすい一方で、機能を1つ変更するだけでも複数のパッケージを行き来することがあります。
逆に私はこのケース以外のアーキテクチャに触れたことがありません。

なので今回は自分の学習を兼ねて、TODOを作成・一覧取得する小さなAPIを、レイヤード構成とVSAの2通りで書き比べ理解していこうという感じです。この記事では、その結果を踏まえて「VSAが向く場面」を整理してみようと思います。

## Vertical Slice Architectureとは

VSAという名前は、Jimmy Bogard氏が2018年に公開した記事で使われています。Bogard氏は、アプリケーションをレイヤーではなく個別のリクエスト（ユースケース）を中心に組み立て、**スライス内の結合を高め、スライス間の結合を小さくする**考え方を示しています。

[Vertical Slice Architecture](https://www.jimmybogard.com/vertical-slice-architecture/)

たとえば、「TODOを作成する」と「TODOの一覧を取得する」は別々のスライスです。それぞれに必要なHTTPハンドラー、入力の検証、永続化を近くに置きます。

```text
TODOを作成する

HTTP request → handler → validation → database
```

ここで重要なのは、レイヤーを完全になくすことではありません。認証、ロギング、データベース接続のように複数の機能から使う仕組みは共有できます。VSAで減らしたいのは、すべての機能が必ず通らなければならない `service` や `repository` のような、アプリケーション全体に共通する抽象化です。

## Goではパッケージの境界も設計になる

Goでは、同じディレクトリにあるソースファイルが1つのパッケージとしてコンパイルされます。つまり、ディレクトリを増やすことは、そのままパッケージとimportの境界を増やすことです。

[How to Write Go Code](https://go.dev/doc/code)

また、サーバーの実装は `internal` に置く構成が公式ドキュメントでも紹介されています。`internal` 配下はモジュール外からimportできないため、外部利用者との互換性を気にせずに整理し直せます。

[Organizing a Go module](https://go.dev/doc/modules/layout)

この性質を考えると、GoでVSAを取り入れるときに、すべてのユースケースを最初から別パッケージにする必要はなさそうです。

```text
internal/
  todo/
    create.go
    list.go
```

このように `todo` パッケージの中でファイルを分けるだけでも、変更の単位を意識できます。ユースケースが育って独立したAPIや依存を持つようになったときに、`todo/create` や `todo/list` へ分ければよいと思います。

## 小さなTODO APIを2通りで書く

今回比べたAPIは、次の2つだけです。

- `POST /todos` でTODOを作成する
- `GET /todos` でTODOの一覧を取得する

どちらの構成でも、TODOを1件作成した後の `GET /todos` は次のJSONを返すことをテストしました。

```json
[{"id":1,"title":"記事を書く"}]
```

検証にはGo 1.26.0（darwin/arm64）と標準ライブラリだけを使い、`go test ./...` を実行しました。

### レイヤード構成

レイヤード構成では、HTTPの入口、ユースケース、データアクセスを技術的な責務で分けます。

```text
internal/
  layered/
    handler/
      todo.go
    service/
      todo.go
    repository/
      todo.go
```

`POST /todos` の変更を追うと、基本的には次の順にコードを読んでいくことになります。

```text
handler → service → repository
```

サービス層に、その機能に固有の検証や複数の操作を組み合わせる処理があるなら、この分け方は自然です。一方で、サービス層がリポジトリを呼ぶだけなら、機能を追加するたびに「通過するためだけの層」が増えることになります。

### VSA構成

VSA構成では、作成と一覧取得を別の変更単位として置きます。

```text
internal/
  vertical/
    create/
      handler.go
    list/
      handler.go
    todos/
      store.go
```

`create` は `POST /todos` だけ、`list` は `GET /todos` だけを扱います。今回のサンプルでは、どちらもインメモリの `Store` を直接利用しています。

```go
func (h *Handler) Register(mux *http.ServeMux) {
	mux.HandleFunc("POST /todos", func(w http.ResponseWriter, r *http.Request) {
		var input struct {
			Title string `json:"title"`
		}
		if err := json.NewDecoder(r.Body).Decode(&input); err != nil {
			http.Error(w, "invalid JSON", http.StatusBadRequest)
			return
		}

		w.Header().Set("Content-Type", "application/json")
		w.WriteHeader(http.StatusCreated)
		_ = json.NewEncoder(w).Encode(h.store.Create(input.Title))
	})
}
```

このコードでは、作成処理を理解するために `service` や汎用的な `repository` をたどる必要がありません。`create` を開けば、HTTPの入力を受けてTODOを保存し、レスポンスを返す流れが見えます。

なお、`"POST /todos"` のようなHTTPメソッドを含む `ServeMux` のパターンはGo 1.22で追加されました。古いGoを使う場合は、`"/todos"` を登録してハンドラー内でメソッドを分岐するか、ルーターを利用します。

[Routing Enhancements for Go 1.22](https://go.dev/blog/routing-enhancements)

## VSAで良かったこと

### 変更箇所の起点が明確になる

「TODO作成時のバリデーションを変えたい」とき、まず `create` を見ればよい、と判断できます。すべてのコードがそこにあるわけではなくても、変更の起点がユースケース名になっているのは分かりやすいと感じました。

レイヤード構成では、最初に `handler`、`service`、`repository` のどこから読み始めるかを考えます。VSAでは、先に「何を変えるのか」を決めてから、そのスライスを開けます。

### 抽象化を必要になるまで増やさずに済む

すべてのユースケースが同じデータアクセスの形を取るとは限りません。作成ではトランザクションが必要でも、一覧取得では読み取り専用のクエリだけで十分かもしれません。

VSAでは、最初から全機能が同じ `Service` や `Repository` を通る前提にしません。重複や複雑さが実際に現れてから、共通化やドメインの抽出を検討できます。

これは「重複を放置する」という意味ではありません。Bogardも、スライスごとの実装からコードの匂いを見つけてリファクタリングすることを前提にしています。VSAは、共通化の判断を早めすぎないための構成でもあります。

### テストをユースケースに寄せやすい

今回のテストは、内部の型や関数の呼び出し順ではなく、HTTP経由の振る舞いを確認しました。

```text
POST /todos が 201 を返す
GET /todos が作成済みの TODO を返す
```

ユースケースごとにテストを考えると、どの層をモックするかよりも「このリクエストは何を保証するか」に意識を向けやすくなります。

## VSAが向いていそうな場面

今回の比較から、次のようなケースではVSAが特に合いそうです。

- HTTP APIやジョブなど、ユースケースを追加・変更する頻度が高い
- 機能ごとに担当やレビューの単位を分けたい
- すべての機能に同じ層や抽象化が必要とは限らない
- 既存の共通層が大きくなり、変更の影響範囲を追いにくくなっている

反対に、VSAだけで解決しないこともあります。

複数のユースケースで同じ複雑なドメインルールを守る場合は、そのルールを適切なドメインの型や関数に置く必要があります。認証、トランザクション、監査ログのような横断的な処理も、スライスごとにコピーするものではありません。

また、スライスを細かく分けすぎると、Goではパッケージ間のimportが増えます。小さなアプリケーションなら、1つの `todo` パッケージに `create.go` と `list.go` を置くだけで十分なことも多いです。

VSAは、パッケージを増やすためのルールではなく、**一緒に変更されるコードを近くに置くための視点**として使うのがよさそうです。

## まとめ

- VSAは、技術レイヤーではなくリクエストやユースケースを中心にコードをまとめる考え方
- Goではディレクトリがパッケージ境界になるため、最初から細かく分けすぎない
- レイヤーを通るだけの抽象化を減らすと、変更の起点と処理の流れを追いやすくなる
- 共通化・ドメインルール・横断的な処理までスライスに閉じ込める必要はない

VSAを知る前は「`handler` / `service` / `repository` をやめる構成」だと思っていました。
実際にはそうではなく、「この機能を変えるとき、どのコードを一緒に見ればよいか」を考えるための構成でした。

まずは既存のアプリケーションを大きく作り替えるのではなく、新しいエンドポイントを1つ追加するときに、機能単位でコードを置いてみるところから試してみようと思います。
